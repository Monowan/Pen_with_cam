# Інтерфейс: ручка ↔ сервер ↔ LED

Опис протоколу між XIAO ESP32-S3 (ручка з камерою) і Flask-сервером,
а також формату керування RGB-світлодіодами у відповіді сервера.

Файли: `SendAndWoitRes.ino` (ESP), `server.py` (реальний Gemini),
`server_test.py` (заглушка для тестів).

---

## 1. Транспорт

ESP надсилає **один HTTP-запит** і читає **всю відповідь як звичайний текст**,
без JSON і без розбору HTTP-статусу.

```
POST /upload HTTP/1.1
Host: <IP сервера>
Content-Type: multipart/form-data; boundary=----PTB<hex>
Content-Length: <довжина тіла>
Connection: close

------PTB<hex>
Content-Disposition: form-data; name="image0"; filename="shot0.jpg"
Content-Type: image/jpeg

<бінарний JPEG кадру 1>
------PTB<hex>
Content-Disposition: form-data; name="image1"; filename="shot1.jpg"
Content-Type: image/jpeg

<бінарний JPEG кадру 2>
------PTB<hex>
Content-Disposition: form-data; name="image2"; filename="shot2.jpg"
Content-Type: image/jpeg

<бінарний JPEG кадру 3>
------PTB<hex>--
```

Сервер також приймає старий формат — **сирий JPEG у тілі** без multipart
(корисно для `curl --data-binary` і ручних тестів).

| Параметр | Значення |
|---|---|
| Метод | `POST` |
| Шлях | `/upload` |
| Тіло | `multipart/form-data`, поля `image0`, `image1`, … (JPEG, FHD, quality 30) |
| Кодування відповіді | UTF-8, `text/plain` |
| Таймаут TCP | 15 с |
| Час очікування Wi-Fi | 15 с |

Сервер **мусить** повернути 200 і тіло відповіді. Будь-яке інше тіло
ESP вважає «відповіддю AI» — але LED-скрипт розпізнає лише за форматом з п. 3.

> Уся відповідь приходить разом із HTTP-заголовками. ESP відрізає все до
> `\r\n\r\n` і парсить **лише тіло**.

## 2. Звичайна відповідь (без підсвітки)

Будь-який текст, що не містить LED-скрипта, просто логують у Serial:

```
Server response:
3
[LED] no LED script in response (answer only)
```

Формати відповіді тесту (задаються промптом на сервері):

| Тип завдання | Формат | Приклад |
|---|---|---|
| одна правильна відповідь | одна цифра | `3` |
| кілька правильних | цифри через пробіл | `1 4 5` |
| встановлення відповідності | пари `цифра-цифра` | `1-3 2-1 3-4` |
| числова відповідь | число, крапка як розділювач | `25.5` |

### 2.1. Відмова: `!FAIL: <причина>`

Якщо сервер **не зміг упевнено розпізнати** завдання, він повертає рядок,
що починається з `!FAIL:` (перший символ — знак оклику). Далі — коротка
причина українською.

```
!FAIL: Недостатньо даних
!FAIL: моделі розходяться у відповіді (2: 2x; 3: 1x)
!FAIL: Недостатньо даних для розв'язання
```

Гарантії:

- відповідь **ніколи не починається з цифри**, якщо сервер не впевнений;
- формат `!FAIL: ...` фізично не збігається з жодним форматом відповіді
  (без цифри на початку, містить літери й `:`), тому приймальний код її не
  сплутає з варіантом тесту;
- причини бувають різні, але початок `!FAIL` — стабільний. ESP/додаток має
  перевіряти `response.startsWith("!FAIL")` і показувати помилку, а не
  «відповідь».

### 2.1.1. Позначка `[ОДНА]` — відповідь без підтвердження

Якщо цифрову відповідь дала **лише одна** модель (решта відмовили або були
недоступні через квоту), сервер **не порівнює** її ні з чим і подає як
відповідь, але з префіксом `[ОДНА] `:

```
[ОДНА] 3
[ОДНА] 4 3 1 2
[ОДНА] 25.5
```

| Ситуація | Відповідь |
|---|---|
| дві+ моделі дали однакове | `4 3 1 2` |
| одна модель дала, інші відмовили/недоступні | `[ОДНА] 4 3 1 2` |
| моделі дали **різне** | `!FAIL: моделі розходяться ...` |
| ніхто не дав цифр | `!FAIL: ...` |

ESP знімає префікс перед розбором тіла і пише в Serial
`[AI] WARNING: single model answer, not confirmed`. Мережево відповідь
лишається придатною, але в логах видно, що кворуму не було.

Коли сервер повертає `!FAIL`:

| Ситуація | HTTP |
|---|---|
| фото розмите / засвітлене / обрізане / перевернуте | 200 + `!FAIL` |
| у кадрі не тестове завдання, немає варіантів | 200 + `!FAIL` |
| моделі AI дали **різні** відповіді (немає кворуму) | 200 + `!FAIL` |
| відповіла лише одна модель, решта відмовили | 200 + `!FAIL` |
| некоректне зображення (Pillow не пройшов `verify`) | 400 `Invalid image` |
| порожній POST | 400 `no image` |

Правило безпеки в `server.py` (`call_gemini`): відповідь видається **лише за
кворумом** — щонайменше дві моделі з `MODEL_CANDIDATES` незалежно дали ту
саму цифрову відповідь. Розбіжність моделей (`2` проти `3`) трактується як
невдача, а не як «більшість вирішила».

### 2.2.1. Порівняння відповідей: канонічна форма

Моделі пишуть ту саму відповідь по-різному, тому порівнюються не рядки, а
**канонічні ключі** (`answer_key()`):

| Що сказала модель | Канонічний вигляд | Тип |
|---|---|---|
| `4 3 1 2`, `4-3-1-2`, `4,3,1,2`, `4312` | `4 3 1 2` | порядок (послідовність) |
| `4 1 3 2` | `4 1 3 2` | інший порядок — **інша відповідь** |
| `1-3 2-1 3-4`, `3-4 2-1 1-3` | `1-3 2-1 3-4` | пари |
| `25.5` | `25.5` | число |

Правила:

- **завдання на впорядкування** (кілька однозначних цифр) — порядок
  **важливий**, бо саме він і є відповіддю; роздільники (пробіл, дефіс, кома)
  рівнозначні, тому `4-3-1-2` = `4 3 1 2` = `4312`;
- **відповідність** (пари з дефісом) — порядок **пар** не важливий (сортування
  за першим елементом), а порядок **усередині пари** важливий: `1-3` ≠ `3-1`;
- злиплі номери (`4312`) розгортаються в окремі цифри, якщо їх 2–4 і всі різні;
  `22`, `100`, `25` лишаються числами;
- лог `same answer written differently: [...]` показує, що різні записи визнано
  однією відповіддю.

### 2.2. Сигнал ручки на відмову

Коли тіло відповіді починається з `!FAIL`, ручка (ESP32-S3):

1. не запускає жодного LED-скрипта;
2. **один раз блимає червоним на 1 секунду** (`blink_red_once`, яскравість R=45),
   після чого гасить світлодіоди;
3. пише в Serial: `[AI] no confident answer (refusal) -> red blink`,
   після відтворення — `[LED] fail blink finished`.

Це саме індикація відмови розпізнавання, а не помилки мережі: втрата Wi-Fi
чи таймаут приходять порожнім тілом і червоного бліку не дають.

### 2.3. Зйомка кількох кадрів і сигнал удалого кадру

За одне натискання ручка робить **три кадри** (`SHOT_COUNT = 3`) з паузою
`SHOT_GAP_MS = 30 мс`. Затримка мінімальна: сенсор налаштований на
`fb_count = 4`, тому кожен наступний `esp_camera_fb_get()` віддає вже готовий кадр.

Кожен **успішно** зроблений кадр сигналізується **дуже коротким бліком
червоного — 40 мс** (`SHOT_BLINK_MS`, `blink_shot()`), після чого LED гаситься.
Три кадри = три короткі блики.

**Що йде на сервер:** усі зняті кадри в одному multipart-запиті. Сервер
оцінює різкість кожного (дисперсія лапласіана після зменшення до 640 px) і
надсилає в Gemini **найрізкіший**; решта зберігаються з суфіксом `_alt.jpg`.

Схема LED-сигналів:

| Подія | Сигнал |
|---|---|
| кадр зроблено (3× підряд) | короткий блік червоного 40 мс |
| сервер не розпізнав (`!FAIL`) | один блік червоного 1000 мс |
| відповідь розпізнано | LED-скрипт (якщо сервер його прислав) |
| мережа/таймаут | без сигналу |

## 3. LED-скрипт (керування підсвіткою)

Якщо тіло відповіді містить валідний скрипт — ESP відтворює його
**після завершення циклу upload**, потім гасить світлодіоди.

### 3.1. Граматика

```
<script>   := <step> ( ";" <step> )*
<step>     := [ "LED:" ] <color> ":" <mode> ":" <ms> [ ":" <gap> [ ":" <reps> ] ]
```

### 3.2. Поля

| Поле | Обов'язкове | Значення |
|---|---|---|
| `LED:` | ні | префікс, опційний |
| `<color>` | **так** | `R` `G` `B` `W` `Y` `C` `M` |
| `<mode>` | **так** | `ON` / `BL` / `SP` |
| `<ms>` | **так** | 30 … 30000 мс; поза межами обрізається |
| `<gap>` | ні | тільки для `SP`: пауза темряви, за замовчуванням = `<ms>` |
| `<reps>` | ні | тільки для `SP`: кількість спалахів, за замовчуванням 1 |

### 3.3. Кольори

| Код | Склад (R/G/B у % яскравості) | Вигляд |
|---|---|---|
| `R` | 45 / 0 / 0 | червоний |
| `G` | 0 / 100 / 0 | зелений |
| `B` | 0 / 0 / 20 | синій |
| `W` | 45 / 100 / 20 | білий |
| `Y` | 45 / 100 / 0 | жовтий |
| `C` | 0 / 100 / 20 | блакитний |
| `M` | 45 / 0 / 20 | пурпуровий |

Яскравості взяті з проєкту `Led_test` (піни R=8, G=9, B=7, 8-бітний ШІМ 5 кГц).

### 3.4. Режими

| Режим | Поведінка | Використання `<ms>` / `<gap>` / `<reps>` |
|---|---|---|
| `ON` | світиться постійно `<ms>` мс, далі одразу наступний крок | `<ms>` — тривалість |
| `BL` | миготіння: половина періоду світло, половина темрява | `<ms>` — **повний період** |
| `SP` | спалах `<ms>` світла, `<gap>` темряви, всього `<reps>` разів | усі три |

### 3.5. Приклади

```
LED:R:ON:300;LED:G:ON:300;LED:B:ON:300;LED:W:SP:100:200:3
```
Червоне 0.3 с → зелене 0.3 с → синє 0.3 с → 3 білі спалахи по 100 мс з паузами 200 мс.

```
LED:G:SP:80:120:2
```
Два короткі зелені спалахи — «впевнена відповідь».

```
R:BL:500
```
Коротка форма без префікса: червоне миготить з періодом 0.5 с (один цикл).

```
LED:Y:SP:100:150:2;LED:M:ON:200
```
Два жовті спалахи, потім пурпурове постійне 0.2 с.

## 4. Обмеження реалізації

| Параметр | Значення | Де змінити |
|---|---|---|
| максимум кроків на відповідь | 12 | `LED_MAX_STEPS` |
| мінімальна тривалість | 30 мс | `LED_MS_MIN` |
| максимальна тривалість | 30000 мс | `LED_MS_MAX` |
| регістр | не важливий (`toUpperCase`) | — |
| пробіли навколо токенів | обрізаються | — |
| невалідний токен | мовчки пропускається | — |
| невалідне тіло | LED не чіпаються, лише лог | — |

Парсер шукає підрядки `LED:`, `ON:`, `SP:` — якщо жодного немає,
скрипт вважається відсутнім.

## 5. Журнал у Serial (115200)

```
Server response:          <- сире тіло відповіді
<тіло>
[LED] script parsed, 4 steps, will run after upload cycle
[LED] playing 4 step(s)
[LED] done
[LED] animation finished
```

## 6. Тестовий сервер

`server_test.py` — заглушка замість Gemini, віддає вручну задану відповідь.

```bash
./.venv/bin/python server_test.py
```

| Ендпоінт | Дія |
|---|---|
| `GET /` | Web UI: поле відповіді, черга, журнал запитів |
| `GET/POST /set?text=...` | задати відповідь на кожен наступний `/upload` |
| `GET /queue` | показати чергу |
| `POST /queue` | додати відповідь у кінець черги |
| `POST /queue` з `clear=1` | очистити чергу |
| `GET /health` | `{"status":"test-stub","answer":...,"queue":N}` |
| `POST /upload` | приймає JPEG, повертає задану відповідь |

Порядок: якщо в `queue.txt` є рядки — береться перший і з'їдається;
коли черга порожня — постійна відповідь із `/set`.
